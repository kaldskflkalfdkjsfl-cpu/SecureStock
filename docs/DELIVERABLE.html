1. Overview نظرة عامة

SecureStock is a complete inventory and sales management system built with Flask, designed as a secure programming exercise. Every layer applies defense-in-depth: strong authentication, role-based access control, encrypted sensitive data, sanitized input/output, transactional business logic, and a full audit trail.

سيكنستوك نظام متكامل لإدارة المخزون والمبيعات بإطار Flask، صُمِّم كتمرين برمجي آمن: مصادقة قوية، تحكم بالصلاحيات، تشفير البيانات الحساسة، تعقيم الإدخال والإخراج، معاملات متكاملة، وسجل تدقيق شامل.

1.1 Functional Scope

  • User management (admin) with pagination
  • Product & customer CRUD
  • Inventory adjustments — quantity never negative
  • Transactional sales — stock check, Sale/SaleItem, atomic rollback
  • TOTP two-factor authentication & password lifecycle
  • Audit-trail viewer (admin only)

3.2 Security Use Cases — exactly 4

  • SUC1 — Secure Login: validate input → locate user → verify scrypt hash (constant-time, dummy-hash for unknown) → lock check → (TOTP if enabled) → session → audit.
  • SUC2 — Authorized CRUD: authenticate → authorize → validate/sanitize → CRUD → audit.
  • SUC3 — Secure Sale Transaction: validate → check stock → Sale → SaleItem → decrement → commit; any exception → full rollback (atomically tested).

5. Security Algorithms in Practice الخوارزميات الأمنية تطبيقياً

5.1 Password Hashing — scrypt app/security.py

generate_password_hash(password, method="scrypt")
# format: scrypt:32768:8:1$salt$hash
  • Memory-hard KDF (RFC 7914) → resists GPU/ASIC parallel brute force.
  • Per-user random salt → resists rainbow tables.
  • Verification uses hmac.compare_digest → constant-time comparison.

5.2 Session & CSRF Signing — HMAC-SHA256

  • Session cookie signed with SECRET_KEY (itsdangerous → HMAC-SHA256 + timestamp).
  • CSRF: synchronizer-token pattern, session-bound, 1-hour expiry (WTF_CSRF_TIME_LIMIT=3600).

5.3 At-Rest Encryption — Fernet

Fernet = AES-128-CBC + HMAC-SHA256 (encrypt-then-MAC) + random IV + timestamp.
Applied to Customer.phone_encrypted; invalid token → [unavailable].

5.4 TOTP 2FA — HMAC-SHA1 (RFC 6238)

TOTP = Truncate(HMAC-SHA1(secret, floor(time/30))) — 6 digits every 30 s, valid_window=1 tolerance; QR via otpauth://totp/SecureStock:...

5.5 Anti-Enumeration / Timing

Login verifies against DUMMY_HASH when the account does not exist, so timing does not reveal account existence; one generic error message in all failure paths.

5.6 Input & Output Hardening

  • SQLi: parameterized ORM queries + LIKE wildcard escaping (%, _, \).
  • XSS: Jinja2 autoescape + bleach.clean() strip-all + length cap.
  • Uploads: extension whitelist + magic bytes (%PDF, \x89PNG, \xff\xd8\xff) + secure_filename + resolved-path containment + 2 MB limit.
  • Regex validation: email, phone, 6-digit TOTP, strong password policy.

5.7 Session Hardening & Headers

HttpOnly · SameSite=Lax · Secure (env) · 8-hour absolute cookie lifetime, plus server-enforced 30-min idle and 8-hour absolute timeouts (config.py:22-26, checked per request in user_loader, __init__.py:31-43). Every session also carries a server-side revocable stamp (User.session_token, models.py:18): rotating it instantly invalidates all other sessions on password change (profile.py:125), admin reset (users.py:108) and "sign out all devices" (profile.py:138-148). Verified by tests/test_session_security.py.
Headers: X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy, strict Content-Security-Policy.

9.1 Security checklist (all automated)

  1. 3 wrong passwords → lockout (timezone-safe)
  2. Unknown email → same error message & timing
  3. Employee → /users/ = 403
  4. Employee opens another employee's sale = 403 (IDOR)
  5. <script> rendered as text (no XSS)
  6. SQL-like search string treated as data
  7. POST without CSRF token = 400
  8. ../../secret.txt upload rejected
  9. PNG renamed to .txt rejected (magic bytes)
  10. Insufficient-stock sale rejected atomically
  11. Negative inventory adjustment rejected
  12. Customer phone encrypted at rest
  13. Passwords stored as scrypt hashes, never plaintext
  14. Login rate limit returns 429
  15. TOTP second factor enforced end-to-end
  16. Admin cannot delete self; reset unlocks account
  17. Every security event recorded in the audit trail
Note: test isolation is guarded — a dedicated test verifies fixtures never bind to the production instance/securestock.db.

12. Likely Discussion Questions أبرز أسئلة المناقشة

Why scrypt and not SHA-256? Memory-hard KDF → resists GPU/ASIC parallel brute force; salted → resists rainbow tables.
Why Fernet for the phone? Encrypt-then-MAC (AES-CBC + HMAC) → confidentiality and integrity; misuse-resistant by design.
Can CSRF be bypassed? Session-bound tokens, 1-h expiry, SameSite=Lax, and SESSION_COOKIE_SECURE in production — layered.
How do you prevent SQLi with LIKE? ORM binds parameters; wildcards explicitly escaped so %/_ stay data.
What if a sale fails mid-write? Commit after the full flow; on exception the DB session rolls back — verified by atomicity tests.
How does lockout survive timezones? UTC storage + naive-datetime normalization.
Why is the login page slow even for unknown users? Deliberate — a dummy scrypt compare equalizes timing (anti-enumeration).
