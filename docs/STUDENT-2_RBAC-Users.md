## 4) نقاط قوتك — تعرفها إجبارياً

1. RBAC بالأدوار الثلاثة admin/manager/employee.
2. زخرفة `role_required` تُفرض على الخادم لا الواجهة (لا تجاوز بتعديل HTML).
3. المستخدمون = admin فقط؛ المنتجات = admin/manager فقط؛ الموظف يقرأ فقط.
4. حذف محمي: لا نفسك، لا صاحب مبيعات.
5. سياسة كلمة المرور تُبنى دالةً وتُفرض في الإنشاء وإعادة التعيين.
6. كلمة المرور تُخزَّن scrypt دائماً.
7. كل عملية تُسجَّل (USER_CREATED / PASSWORD_RESET / PRODUCT_*).
8. 12 اختباراً في test_rbac تثبت الزخارف على كل مسار.

## 5) دليل العرض الحي (تنفذه أمام الدكتور)

1. سجّل دخول admin (`admin@securestock.example.com`).
2. أنشئ مستخدماً بدور manager بقوة كلمة المرور → نجاح + تدقيق USER_CREATED.
3. اخرج ودخول بحساب employee ← جرب فتح `/users` → **403**.
4. من نفس حساب employee حاول تعديل منتج → **403**.
5. عد لأدمن ← أفلتر تدقيق PASSWORD_RESET ← قبل ذلك نفّذ إعادة تعيين كلمة مرور وصدّق الرسالة.

## 6) أسئلة المناقشة المتوقعة + إجاباتك النموذجية

**س1: اشرح RBAC في مشروعك.**
ثلاثة أدوار: admin يدير المستخدمين والتدقيق وكل العمليات؛ manager يدير المنتجات والعملاء والمخزون والمبيعات؛ employee يقرأ المنتجات وينشئ مبيعاته ويرى مبيعاته فقط. التزام يُطبق بالديكور `role_required` الذي يفشل بدالة 403 عند مخالفة الدور، على مستوى الخادم.

**س2: ماذا لو حاول موظف فتح `/users` مباشرة؟**
يُرفض 403 لأن الديكور يُفحص قبل تنفيذ المسار. الدليل: `users.py:20` + `security.py:122-132`. سلوك غير قابل للتجاوز من الواجهة.

**س3: كيف تضمن أن كل المسارات الحساسة مغطاة بالزخرفة؟**
اختبارات RBAC (12 اختباراً) تسجل الدخول بكل دور وتفحص 200/403 على كل مسار؛ نسيان الزخرفة يكسر الاختبار فيظهر الخطأ فوراً. الديكورات: `users.py:20,31,65,84` و`products.py:28,51,73`.

**س4: ما سياسة كلمة المرور وكيف تُنفَّذ؟**
10–128 حرفاً وتشترط حرفاً كبيراً وصغيراً ورقماً ورمزاً عبر `validate_password` (`security.py:40-44`)؛ تُفرض في إنشاء المستخدم `users.py:40-45` وإعادة التعيين `:95-100`.

**س5: كيف تحمي إعادة تعيين كلمة المرور؟**
مسار بأدمن فقط، يستبدل التجزئة وتفريغ `failed_attempts` وكسر القفل فيُعيد فتح الحساب، مع تسجيل PASSWORD_RESET. `users.py:82-115`.

**س6: لماذا لا يحذف المدير نفسه؟**
لمنع ترك النظام بلا مدير. الفحص قبل التنفيذ `users.py:70-72` — وقرار تفويضي صريح في مصفوفة الصلاحيات.

**س7: ما الحماية عند حذف مستخدم له مبيعات؟**
`IntegrityError` من قاعدة البيانات يُعالَج بتراجع `rollback()` ورسالة واضحة — لا حذف يخالف المفاتيح الأجنبية. `users.py:73-79`.

**س8: هل يمكن أن يتخطى الموظف صلاحيات التعديل؟**
لا — التفرقة ليست في الواجهة بل في الخادم: القراءة مفتوحة للكل، لكن الكتابة محصورة في admin/manager عبر `role_required` وهو يفحص الدور قبل أي تعديل/حذف.

**س9: كيف تحقق CRUD للمنتجات كاملاً؟**
إنشاء `products.py:26-47`، قراءة (قائمة+بحث) `:11-24`، تعديل `:49-69`، حذف `:71-80` — مع تعقيم النصوص `:33-34` و`58-59` وتدقيق كل عملية.

**س10: كيف يتم إنشاء المستخدم بأمان خطوة بخطوة؟**
نموذج WTForms يتحقق من الشكل ← فحص بريد مكرر ← سياسة كلمة مرور ← `hash_password` (scrypt) ← حفظ مع تدقيق USER_CREATED. `users.py:33-58`.

## 7) افتتاحيتك الجاهزة (30 ثانية)
"نطاقي هو من يدخل النظام وماذا يجوز له. بنينا RBAC بثلاثة أدوار تُفرض على الخادم عبر زخرفة role_required على كل مسار، فغطينا سلوك الموظف والمدراء لا الواجهة. ومن جهة التشغيل: إدارة مستخدمين آمنة — إنشاء بتجزئة scrypt، حذف محمي لا يمس النفس ولا أصحاب المبيعات، وإعادة تعيين تكسر القفل — مع CRUD كاملة للمنتجات وسياسة كلمة مرور صارمة، وكل فعل مسجل في سجل التدقيق."
